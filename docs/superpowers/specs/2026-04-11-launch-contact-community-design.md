# KnowYou 联系入口、社区与正式上线基础设施设计

## 1. 背景与目标

当前 KnowYou 已经具备核心产品能力，但缺少正式面对真实用户时最基本的外部承接设施：

- 用户不知道如何联系作者
- 产品内没有稳定的社区入口
- 仓库缺少对外可见的隐私、条款、社区说明与支持信息
- 正式上线所需的法律与分发准备项尚未被集中梳理

本次设计的目标不是扩展核心采集或日记能力，而是补齐“产品可以被用户找到、联系、理解、反馈、加入社区、并具备初步上线可信度”的基础设施。

本次工作需要同时覆盖两个层面：

1. 应用内可见入口
2. 仓库与对外文档

## 2. 设计范围

### 2.1 In Scope

- 在应用内新增作者联系与社区入口
- 明确展示 X/Twitter、邮箱、Discord 社区入口
- 在应用内展示版权信息与公司英文名
- 为仓库补充隐私政策、使用条款、社区说明、上线清单
- 在 README 中补充 Contact / Community / Support 信息
- 为 Discord 社区准备默认结构、频道说明、欢迎文案与规则文案
- 梳理正式上线前仍需准备的关键资产与检查项

### 2.2 Out of Scope

- 不在本次引入用户账户系统
- 不在本次实现应用内消息提交后端
- 不在本次接入在线客服系统
- 不在本次真正自动创建 Discord 服务器或替用户完成第三方平台登录授权
- 不在本次完成官网建设
- 不在本次修改核心日记生成逻辑

## 3. 外部入口策略

### 3.1 联系方式

产品对外联系信息统一采用以下两条：

- X/Twitter: `https://x.com/TianfuW49629`
- Email: `cestlouiswu@gmail.com`

设计原则：

- 应用内和仓库文档中的联系信息必须保持一致
- 联系方式以“可直接点击”而不是“纯文本展示”为主
- 应用内应优先支持一键打开链接或发邮件

### 3.2 社区平台选择

社区平台采用 Discord 作为主社区。

原因如下：

- 比微信群、Telegram 更适合沉淀长期讨论与公告
- 比 GitHub Discussions 更适合非代码用户参与
- 支持规则频道、公告频道、角色、邀请入口等标准社区结构
- 后续如果产品形成稳定用户群，Discord 的频道分层比即时聊天工具更容易维持秩序

本次不会承诺程序化创建 Discord 社区，而是把以下内容准备完整：

- 产品内 Discord 入口位
- README / COMMUNITY 文档中的社区入口说明
- Discord 服务器建议结构
- 频道文案与规则文案
- 需要你手动完成的最后一步操作说明

## 4. 应用内信息架构设计

### 4.1 放置位置

本次不新增独立窗口，也不扩展 onboarding 流程。联系与社区信息放入 Settings 页面新增的 `About & Community` 区域。

这样做的原因：

- Settings 已经是“状态、配置、系统说明”的次级承接页，语义一致
- 不打断当前五步 onboarding 的主线
- 避免为了静态信息引入新的导航结构
- 便于未来继续补充版本号、官网、支持页、隐私政策入口

### 4.2 About & Community 区域内容

该区域应包含以下内容块：

1. Product
- 应用名称：KnowYou
- 产品一句话说明
- 当前版本号与 build（如果现有工程容易读取）

2. Contact
- Follow on X / Twitter
- Email the developer

3. Community
- Join Discord Community
- 一句简短说明：适合讨论产品想法、反馈使用体验、分享你的日记工作流

4. Legal
- Copyright 文案
- 公司英文名
- 隐私政策入口
- 使用条款入口

5. Support
- README / Support 文档入口（如果使用本地文档则打开仓库文档或网页链接；若暂时没有独立 support 页，则先用 README 中的 Support 段承担）

### 4.3 交互原则

- 所有外部入口都应表现为按钮或可点击链接
- 邮箱入口优先使用 `mailto:`
- X/Twitter 与 Discord 使用浏览器打开
- 文本说明保持简洁，不堆叠长段法律文案
- 法律正文不直接塞进 Settings，Settings 只提供摘要与入口

## 5. 仓库与对外文档设计

### 5.1 README 调整

README 新增以下部分：

- Contact
- Community
- Privacy
- Support

要求：

- 联系方式、Discord 入口、支持邮箱与应用内一致
- 对外先明确产品是本地优先的 macOS 应用
- 让首次访问仓库的人能快速知道：这是什么、怎么联系你、怎么加入社区、隐私边界在哪里

### 5.2 新增文档

建议新增以下文件：

1. `PRIVACY.md`
目标：解释 KnowYou 如何采集、过滤、存储和导出数据。
应覆盖：
- 收集哪些数据
- 数据来自哪里
- 何时发生隐私过滤
- 数据默认存放在本机哪里
- 何时可能调用第三方总结器
- 用户如何禁用或控制相关能力
- 联系邮箱

2. `TERMS.md`
目标：给正式上线前一个基础使用条款占位。
应覆盖：
- 软件按现状提供
- 用户对自己输入第三方服务的数据负责
- 不承诺零错误或持续可用
- 禁止违法使用
- 联系方式
- 版权主体

3. `COMMUNITY.md`
目标：定义 Discord 社区的定位、行为规则、反馈方式。
应覆盖：
- 社区用途
- 如何提问 / 提反馈
- 基本行为规范
- 违规内容边界
- 作者联系入口

4. `LAUNCH-CHECKLIST.md`
目标：集中管理正式上线前的实际准备项，避免遗漏。

## 6. Discord 社区结构设计

### 6.1 推荐服务器名称

建议使用：`KnowYou Community`

如果你后续想更个人化，也可以采用：`KnowYou by Tianfu`

本次文档默认使用 `KnowYou Community`。

### 6.2 推荐频道结构

推荐最小可运行结构如下：

- `#welcome`
- `#announcements`
- `#general`
- `#show-your-story`
- `#feedback`
- `#bug-reports`
- `#off-topic`

如果需要一个管理区，可另外加：

- `#mod-notes`（私有）

### 6.3 各频道职责

- `#welcome`：介绍社区用途、产品定位、行为规范、如何开始
- `#announcements`：版本更新、重要变化、公开 roadmap
- `#general`：日常讨论
- `#show-your-story`：用户展示自己的使用方式、日记工作流或截图
- `#feedback`：产品建议、痛点、功能想法
- `#bug-reports`：可复现问题、环境信息、日志线索
- `#off-topic`：非核心话题，避免主区过载

### 6.4 角色建议

最小角色集合：

- `Founder`
- `Moderator`
- `Member`

不建议在早期阶段设计复杂身份体系。社区在冷启动时应尽量低摩擦。

### 6.5 欢迎文案原则

欢迎文案应强调：

- KnowYou 是本地优先、macOS 原生、自动生成工作日记的产品
- 这里适合讨论使用体验、反馈问题、提出想法
- 如果涉及隐私问题或个人账户信息，建议直接发邮件而不是公开发帖

## 7. 法律与品牌信息设计

### 7.1 版权主体

根据你的要求，本次先使用直译英文名作为占位：

`Shanghai Two-Person Beiwu Software Co., Ltd.`

版权展示格式建议：

`Copyright © 2026 Shanghai Two-Person Beiwu Software Co., Ltd. All rights reserved.`

### 7.2 风险说明

该英文名目前仅作为占位版本，不保证与工商/法定英文主体完全一致。

因此文档中不应把它描述为“经正式注册确认的唯一英文法定名称”，而应直接作为当前版权主体展示文本使用。后续如果你拿到正式英文主体名称，需要统一替换应用内和文档中的对应字段。

## 8. 正式上线前需补的内容

除了本次会直接落地的联系入口、社区和版权信息外，正式上线前通常还应准备以下项目：

### 8.1 分发与平台资产

- 应用图标最终版
- 应用截图
- 版本说明
- 下载页或官网落地页
- Support URL
- Privacy Policy URL
- Marketing URL（如果走平台分发）

### 8.2 macOS 分发准备

- Developer ID 签名
- notarization
- 发布包验证
- 首次下载与安装路径说明
- 权限申请说明截图

### 8.3 支持与反馈闭环

- bug report 模板
- FAQ 或已知问题页
- 社区入口稳定邀请链接
- 邮件支持 SLA 的最低预期说明（哪怕只是“通常会尽快回复”）

### 8.4 法律与合规

- 隐私政策正式 URL
- 使用条款正式 URL
- 第三方模型服务的使用说明
- 如果未来收集网站分析、邮箱订阅或云端账户数据，需要单独扩展隐私披露

## 9. 错误处理与边界

- 如果 Discord 邀请链接尚未创建，应用内先显示占位文案或暂不展示按钮，但文档里要明确“社区入口待补”
- 如果版本号读取实现成本过高，本次允许先不在 Settings 动态展示 build 信息
- 如果本地 Markdown 法律文件无法在应用内直接良好打开，Settings 可以先展示摘要文本，完整正文留在仓库文档中
- 如果后续改成官网承载隐私和条款，当前仓库文档内容应保持可迁移

## 10. 测试与验收

### 10.1 应用内验收

- Settings 中出现新的 `About & Community` 区域
- X/Twitter 按钮能打开正确链接
- Email 按钮能触发 `mailto:cestlouiswu@gmail.com`
- Discord 按钮在存在链接时能打开社区链接
- 版权与公司英文名可见
- 隐私政策与使用条款入口可见且指向明确目标

### 10.2 文档验收

- README 出现 Contact / Community / Privacy / Support 段
- `PRIVACY.md`、`TERMS.md`、`COMMUNITY.md`、`LAUNCH-CHECKLIST.md` 存在
- 文档中的联系方式一致
- Discord 社区说明与应用内口径一致

### 10.3 内容验收

- 法律文本不夸大不存在的能力
- 隐私说明与当前真实架构一致，即本地优先、过滤先于持久化、第三方总结器为可选增强
- 上线清单覆盖分发、法律、支持、社区四类事项

## 11. 实施建议

本次实现建议按以下顺序推进：

1. 先补文档与常量来源，确定对外口径
2. 再把应用内 Settings 的 About & Community 区域接上
3. 最后跑测试并更新 architecture / requirements 中与对外入口相关的描述

这样可以降低 UI 先做完但文案口径尚未收敛的返工风险。
